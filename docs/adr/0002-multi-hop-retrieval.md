# ADR-0002：多跳图检索

- 状态：已接受
- 日期：2026-09-17

## 背景

v0.1 的图检索只有一跳：取实体检索的 top-1，调一次 `list_relations`，产出定长三元组 `(源实体名, 关系类型, 目标实体名)`。这让「疾病 → 药物 → 其他适用疾病」「疾病 → 症状 → 相关疾病」这类关联完全无法表达。

真实库的规模决定了硬约束（SQLite 27510 实体 / 328347 关系 / 115669 chunks，Neo4j 完全一致）：

| 事实 | 数值 | 影响 |
|---|---|---|
| 平均出度 | 37.3 | 逐层扩展必须有预算 |
| `TREATED_BY` 科室 fan-in | 最高 795（呼吸内科） | 二跳必然严重截断 |
| `HAS_SYMPTOM` 症状 fan-in | 最高 1001（头痛） | 朴素二跳直接爆炸 |
| `relations` 的索引 | 原先只有主键 | 无索引二跳实测 29448 行 / 92.5ms 全表扫描 |

朴素二跳的代价不是「慢一点」，而是路径数按出度相乘增长；因此本决策的核心不是「要不要多跳」，而是**如何在多跳必然截断的前提下，仍然让截断可见、让正确性判定不依赖截断**。

## 决策

### 1. 逐层扩展，不用变长路径查询

Neo4j 侧每层一次 Cypher 往返（`UNWIND $node_ids` + 每节点 `collect()` 后切片），而不是 `MATCH (a)-[*1..3]->(b)`。理由：变长路径无法对**每个中间节点**单独施加 fanout 预算，也无法拿到「该节点真实边数」用于截断提示；逐层方案可以同时返回真实边数与截断后的前 N 条。

### 2. fanout 预算 + 截断显式化

每跳每节点 fanout = 32，单次遍历总路径上限 200。**截断不隐藏**：`PathTruncation` 记录 `entity_id / total_edges / shown_edges`，随 `GraphPath` 一路传到 API JSON 与网页（「呼吸内科共关联 795 条，本次仅展示前 32 条」）。

### 3. 遍历语义只写一遍

三个后端不各写一份 BFS（三份实现必然漂移）。仓储只实现**唯一一个新原语** `expand_frontier`，BFS、防环、节点唯一性、排序、逐层限额全部放在共享的 `retrieval/traversal.py`。因此「SQLite 图后端实现相同的逐层遍历」是结构上成立的，而不是靠人工对齐。

遍历语义规范见 [文本检索设计](../retrieval.md#多跳遍历语义规范)。

### 4. 推导关联绝不进入 `Claim`

证据按跳数分流：`hop_count == 1` 是**原文事实**，`hop_count > 1` 是**推导关联**。生成器只接收原文事实，因此 `Claim` 在数据流上不可能来自多跳推测 —— 这由 `AnswerService` 的数据流保证，而不是靠提示词约束。推导关联由 `AnswerService` 确定性地渲染成独立区块，文案明确写「由其他实体的记录经图路径推导，不是本实体的原文结论」。

没有任何一跳证据时返回 `insufficient_evidence`，**不从推导关联单独作答**。

### 5. 冲突只判同源直接冲突

同一疾病对同一食物/药物同时有 `SHOULD_EAT` 与 `SHOULD_NOT_EAT` 才算冲突。不同疾病给出相反建议是正常的，跨疾病相反关系不参与判定。真实库中存在 201 组这样的同源冲突对。

### 6. 一跳行为逐位不变

`Evidence.id` 仍是 `sha256("graph\x1f{relation_id}\x1f{chunk_id}")` 的前 20 位；一跳分数沿用 v0.1 公式（跳数衰减在 1 跳时指数为 0）。`tests/test_graph_retrieval.py` 用**硬编码的公式副本**做回归护栏。

## 实现阶段由真实数据暴露的三处缺陷

三处都不是设计评审能发现的，都是拿真实库跑出来才暴露：

1. **多跳完全不可见**：跳数衰减保证一跳分数恒高于多跳（一跳最低 0.65 > 二跳最高 0.6），一跳证据占满 top-k，`derived_association_count` 恒为 0。→ **决策：给多跳保留配额**，`budget = limit // 2`，再按跳数层级均分，否则二跳会把三跳全挤掉。
2. **冲突判定被截断吃掉**：`绝经与心血管疾病 × 杏仁`（60 条边）、`肝胃不和 × 鸡蛋`（53 条边）的冲突对排在 fanout=32 之后被整体丢弃，`conflicting_evidence` 永不触发（v0.1 的 `list_relations(limit=20)` 同样丢，属既有潜伏缺陷）。→ **决策：冲突检测脱离遍历**，仓储新增 `find_opposing_relations`，由 `AnswerService` 直接查图。截断只影响召回，不再影响正确性判定。
3. **最深一层被整体丢弃**：`traverse_paths` 末尾统一 `collected[:limit]`，`max_hops=3` 时路径池 `{1: 32, 2: 168}` 已占满 200，**一条三跳都没有**。→ **决策：逐层各保留至多 limit 条**。

## 结果

### 积极影响

- 「疾病 → 药物 → 其他适用疾病」这类关联可以被表达，且每条关系都能回溯到 DUTMed 原文；
- 三个图后端在遍历上行为一致，可对照验证；
- `Evidence` 新增契约级校验：`chunk_id` 必须出现在路径某一步的关系证据中；
- 截断对使用者可见，不再是静默的信息丢失。

### 权衡

- 一跳候选池从 v0.1 的 `list_relations(limit=20)` 变为逐层 fanout=32，高扇出实体的一跳结果会变化（召回更好，但不是「逐位不变」）；
- `limit` 下的多跳配额会让相同 `limit` 的一跳证据少一半（`max_hops=1` 时不受影响）；
- 评测口径固定为单跳（`_EVALUATION_MAX_HOPS = 1`）：金标准是原文事实 chunk，推导关联会占用 top-k 名额并把金标准挤出，使 recall 假性下降 —— 那是口径变化，不是质量变化。

## 后续发现并一并修复的问题

**Neo4j 与 SQLite 的实体检索排序不一致。** `Neo4jGraphRepository.search_entities` 原本用 Cypher `CONTAINS` + `ORDER BY size(name) DESC`，而 SQLite/内存用共享的 `rank_entities`（双字片段相似度）。查询「乳糜尿」时前者把 `脂肪尿和乳糜尿检查(Chyluria)` 排在首位，后者把 `乳糜尿` 排在首位 —— **起点不同，整条多跳路径和答案都不同**，换后端就换了结果。现已让三个后端共用 `rank_entities`，并用 `tests/test_graph_port.py` 守卫端口的签名一致性。

该分歧在 v0.1 的单跳下同样存在，只是多跳把它放大成了「答案不同」。
