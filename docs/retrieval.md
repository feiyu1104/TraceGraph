# 文本检索设计

## 文本检索 baseline

M2 先建立一个完全离线、结果可重复的关键词检索 baseline。它的作用是验证统一 `Evidence` 输出、版本隔离和后续评测流程，不用于替代向量检索或中文分词系统。

## 检索范围

检索器遍历每份文档的最新版本，旧版本保留用于溯源，但不会进入当前召回结果。这样可以避免已经失效的内容与新版本同时支持回答。

每个命中的 Chunk 会转换为 `Evidence`，包含：

- 文档、文档版本和 Chunk ID；
- 来源名称和标题定位；
- 原始片段内容；
- `keyword` 检索方法和匹配分数。

Evidence ID 根据检索方法和 Chunk ID 稳定生成，同一片段重复检索不会产生新的引用身份。

## 评分方式

- 英文和数字按词归一化；
- 连续中文按双字片段拆分；
- 基础分数是查询词项的命中比例；
- 完整查询作为子串出现时增加奖励；
- 分数限制在 0 到 1，结果按分数降序排列。

这一评分只提供透明、可测试的起点。它不能理解同义词、否定关系、专业缩写或语义相似度。引入向量检索前应先用固定评测集记录 Evidence Recall@k，之后比较增益，而不是直接替换 baseline。

## HTTP 接口

`POST /retrieval/search` 接收查询文本和返回数量，响应中的每一项都是完整 `Evidence`，包括原文、来源、标题位置、版本、Chunk ID、检索方法和分数。接口只负责检索，不调用 LLM，也不会生成自然语言答案。

项目不附带自造语料生成的基线报告；使用 DUTMed 人工标注集评测的方法见评测指南。

## 图检索

医疗 JSON 导入时，疾病字段会映射为实体和关系，每条关系保存支持它的 Chunk ID。`GraphRetriever` 先匹配问题中的实体，再根据“症状、检查、科室、治疗、宜吃、忌吃”等意图对关系排序，最终把关系路径和来源 Chunk 转换成 `Evidence`。

实体检索的排序由 `storage/graph.py` 的 `rank_entities` 统一定义，**三个图后端共用同一份实现**。查询词包含实体名时按「2.0 + 名称长度占比」计分，否则按双字片段相似度（阈值 0.5）计分，同分时按名称、ID 升序。Neo4j 不做 Cypher 侧预筛 —— 换后端不能换起点，起点一变整条多跳路径都会变。

## 多跳图检索

默认 2 跳，上限 3 跳，由 `max_hops` 控制。遍历语义只写一遍：仓储只负责实现 `expand_frontier` 这一个原语，BFS、防环、排序和逐层限额都在 `retrieval/traversal.py` 的 `traverse_paths` 里。

### 多跳遍历语义规范

1. 起点 ∈ `start_entity_ids`；路径长度 1..`max_hops`。
2. **路径内节点不重复**（自环直接忽略）。
3. 每步方向 ∈ 允许方向（`None` = 双向）；每步关系类型 ∈ 允许类型（`None` = 全部）。
4. **每跳 fanout**：对 frontier 中每个节点，其可用边按 `(关系类型, 邻居实体 ID, 关系 ID)` 升序排序后取前 32 条。
5. frontier 规模上限 = 请求的 `limit`。
6. 结果按 `(跳数, 各步关系 ID, 各节点 ID)` 升序排序，**每个跳数层级各保留至多 `limit` 条**。

第 6 条的「逐层限额」不是可选项：若在末尾统一截断，浅层路径会占满名额并把最深一层整体挤掉，使 `max_hops` 形同虚设。

### 截断可见性

某一跳的邻居数超过 fanout 时，`PathTruncation` 记录该节点的真实边数与实际展示条数，随路径一路传到 API 响应和网页提示（「呼吸内科共关联 795 条，本次仅展示前 32 条」）。截断只影响召回，不影响正确性判定 —— 冲突检测直接查图，不走遍历。

### 评分与跳数衰减

路径分数 = 各步分数均值 × `0.6 ** (跳数 - 1)`。

单步分数：基础 0.45，起点为出边时加 `0.35 / (rank + 1)`、入边时加 `0.2 / (rank + 1)`，关系类型命中查询意图再加 0.2，上限 1.0。起点只取实体检索的 top-1，因此 `rank` 恒为 0。

1 跳时衰减指数为 0，分数与 v0.1 完全一致；2 跳最高 `0.725 × 0.6 = 0.435`，稳定低于任何 1 跳。**意图只影响排序、不做硬过滤** —— 意图识别错了只是排序变差，硬过滤则会直接丢掉正确路径。

因为一跳分数恒高于多跳，`max_hops > 1` 时会给多跳保留配额：一跳证据最多占 `limit` 的一半，其余名额按跳数层级均分给推导关联。`max_hops = 1` 或 `limit = 1` 时没有多跳名额，退化为取前 `limit` 条。

### 证据分层

`Evidence.graph_path` 是带方向的完整路径（`GraphPath`：起点 + 每步的 `relation / direction / target`），`hop_count == 1` 是**原文事实**，`hop_count > 1` 是**推导关联**。

- 生成器**只接收原文事实**，因此 `Claim` 在数据流上不可能来自多跳推测；
- 没有一跳证据时返回 `insufficient_evidence`，不从推导关联单独作答；
- 推导关联由 `AnswerService` 确定性地渲染成独立区块，明确标注不是本实体的原文结论。

路径上的每条关系都能回溯原文：`GET /graph/relations/{relation_id}/evidence` 按需返回该关系对应的 DUTMed 原文片段，供界面点击路径中的关系时懒加载。

## 混合检索

`HybridRetriever` 使用加权 reciprocal-rank fusion 合并关键词和图检索。当前图检索权重为 4，用于让结构明确的疾病关系优先于弱关键词重合。这个经验值尚未经过 DUTMed 人工标注集校准，正式使用前需要重新评测。
